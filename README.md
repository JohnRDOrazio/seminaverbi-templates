# SeminaVerbi shared templates

The `SV …` templates and `Module:SV/…` Lua modules used on every SeminaVerbi wiki
(`en it es fr de pt`.seminaverbi.bibleget.io). **This repository is the source of truth:** the
pages on the wikis are overwritten by the sync script, so edit them here and open a pull request.

- `modules/SV/*.lua` → `Module:SV/*`
- `templates/<name>.wikitext` → `Template:<name>` (and `templates/SV infobox/styles.css` → TemplateStyles)
- `config/*.json` and `i18n/*.json` → compiled into `Module:SV/Data`
- `config/categories.json` → the category tree (fields + Gospel themes, six languages), also compiled into `Module:SV/Data`
- `server/` → maintenance script that fills Wikibase items from Wikidata (runs on the server)
- `skills/seminaverbi-editor/` → the Claude Code skill for editing the wikis through the `seminaverbi` MCP server
  (`mcp/`); `templates.md` and `categories.md` are generated by `python -m tools.skilldocs`
- `tools/categories.py` → checks a wiki's categories against the tree and creates the missing ones
- `tools/cleanup_articles.py` → converts old Bible quote and reference-list calls to the SV templates and
  removes Wikipedia's page-maintenance templates (`config/cleanup.json`); dry run by default

Design: `docs/superpowers/specs/2026-11-14-shared-templates-design.md`,
`docs/superpowers/specs/2026-11-17-wiki-mcp-design.md`.

## Editing the wikis with Claude Code

Install the skill once: `ln -s "$PWD/skills/seminaverbi-editor" ~/.claude/skills/seminaverbi-editor`.
The MCP server is described in `mcp/README.md`. After changing `config/templates.json`,
`config/categories.json`, aliases or i18n, run `python -m tools.skilldocs` (the tests fail if the
generated files are stale).

Category check, with the editor bot's credentials (`SV_EDITOR_USER` / `SV_EDITOR_PASSWORD`):

```
python -m tools.categories check --wiki fr [--create] [--dry-run]
```

## The article pipeline

`python -m pipeline` finds film and television candidates for new articles, judges them with Jev, and posts
proposals on the English wiki (`Semina Verbi:Article proposals/…`) for the approved users to vote on.
Design: `docs/superpowers/specs/2026-11-20-article-pipeline-film-design.md`.

Stages (each records its outcome per candidate, so a run resumes where it stopped):

0. `candidates`: the Vatican list of films, the SIGNIS and Ecumenical Jury awards, and Wikidata facets (SPARQL).
1. `covered`: drop what SeminaVerbi already covers on all six wikis; mark partial coverage as a translation.
2. `triage`: drop episodes, trailers, clips and facet-only candidates under the sitelink floor.
3. `quick`: Jev judges the Wikipedia lead; below `quick_drop` the candidate is dropped.
4. `dossier`: notes from the Wikipedia lead and sections (for a series, its season pages with their episode
   summaries) and Wikiquote, in up to three languages.
5. `adjudicate`: Jev decides connection, field and themes (themes read over the whole dossier, in parts), picks
   evidence and builds the outline; a candidate with no theme at 0.50 is dropped unless Jev is confident (0.80) of a direct Christian influence.
6. `publish`: writes the `{{SV proposal}}` pages and the ranking page.

Literature (`--domain literature`) runs the same stages over books, poems and series. Candidates come from the
configured authors, Wikidata facets (Jesus, the Bible, saints, biblical characters, Christian genres), the works
the Illustrissimi letters name and the works of Pope Francis's 2024 letter on reading. A series is one page: its
volumes are folded into it and the dossier reads each volume's page. Works under the sitelink floor are dropped,
except those the Illustrissimi or Francis lists name directly. Religious texts (scripture, its books and parts,
apocrypha, other religions' sacred texts) are dropped at triage; musical works (musicals, operas) are moved to the
`music` domain, where they wait for its stages. Illustrissimi links that are redirects are followed to
their target; only links with no Wikidata item, or people and items with no literary work, are reported. The dossier
adds Wikisource pages to the proposal's sources as links only (they are never read). Run `python -m pipeline calibrate
--domain literature` first, to check the cut-offs against the articles SeminaVerbi already has.

Music (`--domain music`) and art (`--domain art`) run the same stages. Music candidates come from the work classes
(songs, hymns, masses, oratorios, operas and the like, found through the class closure), genres, facets and artists;
bands and groups are reported and skipped, as are people. Rows from facets and genres need 10 sitelinks, rows whose
only source is an artist need 20 (`music.sitelink_floor`, `music.artist_sitelink_floor`); a part (a movement, an
act) is folded into its whole. Art candidates come from what a work depicts, Iconclass codes (Wikidata's P1257
only), genres and a curated list; the floor is 15 sitelinks (`art.sitelink_floor`) and rows from the curated
`list` pass without it. Jev's quick question for art asks about significance, not plausibility. Recordings and
editions, and art copies, are dropped at triage. Run `python -m pipeline calibrate --domain music` (or `art`) and read the
report before the first `publish` of that domain.

**Art benchmark.** `calibrate --domain art` also adds a benchmark of 21 works (strong, implicit and controls) held back as
calibration rows. Open item: the author approves the benchmark list in `art.benchmark` before the first live art
run; this is not done yet. A benchmark work is released one QID at a time with
`python -m pipeline release-benchmark QID [QID ...]`, which turns it into a live candidate that runs stages 1-5 again:
the sitelink floor, the quick drop and `max_new_per_run` apply to it as to any candidate, so it becomes a proposal
only if it passes them, not because it passed them as calibration (a QID that is not a benchmark row changes nothing
and makes the command exit with an error).

Commands (options `--db PATH`, default `data/pipeline.sqlite`, and `--domain`, default `film`, go before or after the command):

```
python -m pipeline candidates|covered|triage|quick|dossier|adjudicate   # one stage
python -m pipeline run [--publish]    # stages 0-5, at most max_new_per_run entering stage 3; publish only with the flag
python -m pipeline calibrate          # add the articles SeminaVerbi already has, run stages 1-5 on them, print the report
python -m pipeline redo STAGE [--qid Q]   # clear that stage and later ones (STAGE 0 is refused)
python -m pipeline skip QID --reason TEXT # drop a row that breaks a stage, at its next stage without an outcome
python -m pipeline release-benchmark QID [QID ...]   # art: turn held-back benchmark works into candidates
python -m pipeline publish | votes | approved
```

`calibrate` prints, per existing article, Jev's connection, field and themes beside the item's `SV field` and
`SV Gospel theme` statements, plus the pages that could not be mapped to Wikidata. Read it before posting anything;
wording or cut-off changes go through a pull request, then `redo`.

The queue is one SQLite file, `data/pipeline.sqlite` (git-ignored; created on first use). It holds the candidates,
their outcomes per stage and Jev's cached answers.

Commands that write to the wiki (`publish`, `run --publish`, `votes`) log in as the editor bot from
`SV_EDITOR_USER` / `SV_EDITOR_PASSWORD`, so run them through `~/.config/seminaverbi/runeditor.py pipeline …`;
`run --publish` checks those credentials before it runs any stage.
Only `quick`, `adjudicate`, `run`, `calibrate` and `press filter|link|run` need `TYPESAFE_API_KEY` (Jev).

**Vote timer.** `votes` counts the votes on open proposals and approves those at the threshold
(`vote_threshold` in `config/pipeline.json`, now 3; `max_new_per_run` and the other cut-offs live there too).
A user timer runs it every 3 hours.

The service assumes this checkout is at `~/development/seminaverbi-templates`: both its `WorkingDirectory` and
its Python (`.venv/bin/python` in the checkout) point there, and a missing `WorkingDirectory` stops the service
from starting. Link the units from the checkout:

```
systemctl --user link "$PWD"/deploy/systemd/sv-pipeline-votes.{service,timer}
```

For a checkout elsewhere, override both paths before enabling the timer, with
`systemctl --user edit sv-pipeline-votes.service` and this drop-in (the empty `ExecStart=` clears the original
command; without it both would run):

```
[Service]
WorkingDirectory=/path/to/seminaverbi-templates
ExecStart=
ExecStart=/path/to/seminaverbi-templates/.venv/bin/python %h/.config/seminaverbi/runeditor.py pipeline votes
```

Then enable the timer:

```
systemctl --user enable --now sv-pipeline-votes.timer
```

The user timer needs systemd (on WSL2, `systemd=true` under `[boot]` in `/etc/wsl.conf`) and, to run while you are
logged out, `loginctl enable-linger $USER`.

**Sources and licences.** Wikidata (CC0) supplies the candidates. Wikipedia and Wikiquote are read as notes for the
writer and Jev, never copied into articles. IMDb and TMDb are not used. The Arts & Faith Top 100 was dropped: it has
no machine-readable list.

### Catholic press

`python -m pipeline press …` reads twelve Catholic outlets (`config/press.json`: L'Osservatore Romano, Vatican News,
Avvenire, Roma Sette, EWTN, La Civiltà Cattolica, Famiglia Cristiana, Aleteia, National Catholic Register, KTO, SIR,
and Gaetano Vallini's blog *Camera con vista*) and feeds every domain. Design: `docs/superpowers/specs/2026-11-23-catholic-media-source-design.md`.

```
python -m pipeline press discover   # new article URLs from each outlet's feeds and sitemaps (round-robin, max_articles_per_run)
python -m pipeline press filter     # Jev: is the article about a work of culture or an artist (culture_drop)? with a faith or values angle (angle_drop)? below either: dropped
python -m pipeline press link       # mentions linked to Wikidata items; kept when Jev finds them discussed substantively; with the article's stance on them (stance_keep)
python -m pipeline press route      # each mention to its domain's queue (source press:<outlet>), the enrichment page, or waiting
python -m pipeline press enrich     # writes Semina Verbi:Press for existing articles on en (editor bot)
python -m pipeline press run        # all five, each article fetched once
python -m pipeline press run --dry-run   # discover, filter, link; prints each mention's would-be route, writes no queue, no wiki
```

`--dry-run` also works with `discover` (into a throwaway store: lists the URLs found per outlet, keeps nothing),
`route` (prints the would-be routes) and `enrich` (prints the page text). Each run ends with the outlets that refused
us (`press refused: …`); a 401/403/429 or a robots.txt rule stops that outlet for the run, never worked around.

The bot reads politely: its own user agent (`SeminaVerbi-press/1.0`, pointing to the page `Semina Verbi:Press bot`,
whose text is `docs/press-bot-page.wiki`), one request at a time per outlet at least `delay_seconds` (10) apart or the
outlet's `Crawl-delay`. A mention whose article is neutral on the work or only critical of it never becomes a candidate or
press evidence; for a work SeminaVerbi covers it goes to the enrichment page, the critical ones marked. The bot keeps the link, title, date, outlet, language and quotations of at most 25 words; never the
full text. Jev reads at most about 150 words per question. Read the `--dry-run` report before the first real run.

**Archives, caps and republished articles** (`vallini`, for now; all per outlet in `config/press.json`):

- An entry with `"walk": true` is an Atom feed (Blogger) whose whole archive is read over successive runs, newest
  change first and cut by date, never by offset; then only its top is read. A post under several labels is one article.
- `max_per_run` bounds the articles an outlet adds, and attempts, per run, inside `max_articles_per_run`; its share (up
  to half of the run) is taken first, so neither it nor the others are starved.
- `article_feed` (a URL with `{path}`) reads an article from its feed entry, for a site whose pages hold no text.
- `republishes` and `author`: a post that states its issue ("L'Osservatore Romano dell'8 novembre 2025", "(©L'Osservatore
  Romano, 23 luglio 2020)") is cited as "Gaetano Vallini, L'Osservatore Romano" with that date, any other as the
  outlet's `name` with the post's date; the link is the post's. The same article in both outlets
  (`pipeline/press/duplicates.py`) is one piece of evidence with both links, whichever came first; the second copy is
  skipped (`skip (duplicate)`). For this pair only, a fingerprint of 64 hashes per article is kept.

`filter`, `link` and `run` need `TYPESAFE_API_KEY`; `enrich` and `run` (without `--dry-run`) log in as the editor
bot first, so run them through `~/.config/seminaverbi/runeditor.py pipeline press …`. `discover` and `route` need
neither.

**Press timer.** `deploy/systemd/sv-pipeline-press.{service,timer}` run `press run` daily at 04:30 through
`runeditor.py`, with `TYPESAFE_API_KEY` from `~/.config/seminaverbi/pipeline.env` (a `KEY=value` file, mode 600).
Link them like the vote timer (same checkout assumptions):

```
systemctl --user link "$PWD"/deploy/systemd/sv-pipeline-press.{service,timer}
```

**Prerequisite:** do not enable `sv-pipeline-press.timer`, and do not run `press filter|link|run` live, before
TypeSafe's written confirmation that it does not train on API inputs is recorded in `docs/content-tasks.md`.

## The category tree on the main pages

Each wiki's main page ends with `{{SV category tree}}` (`modules/SV/Categories.lua`): a card per
top-level field, collapsible branches, the Gospel themes as chips, and article counts.

- **Counts** come from `mw.site.stats.pagesInCategory`, an expensive parser function: one call per
  category, about 190 per page. The farm's `LocalSettings.php` raises `$wgExpensiveParserFunctionLimit`
  to 300 for this. A failed or over-limit lookup shows no count rather than an error. Counts are computed
  when the page is parsed, so a cached main page costs nothing; purge it to refresh them.
- **Only articles count.** `{{SV infobox}}` and `{{SV categories}}` file the field and theme categories
  in the main namespace only, so a sandbox or template page showing an item's infobox stays out.
- **TemplateStyles on the farm rejects `var()`**, and one bad value makes the sync refuse the whole
  stylesheet (the old one stays live). Use plain colours.
- **Night mode:** style it under `html.skin-theme-clientpref-night` and, inside
  `@media (prefers-color-scheme: dark)`, `html.skin-theme-clientpref-os`. The site's night-mode rule
  for the main page resets the background of every element except `.notheme`, so the cards, chips and
  badges carry `notheme`; Vector then gives `.notheme` the day text colour, so the night palette sets the
  text and link colours too. Check the page in both themes after a change.
